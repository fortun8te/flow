# Polish eval

58 messy dictation and selected-text samples with expected outputs. Two ways to run them:

## 1. Replay (offline, no key, Flow can keep running)

Recorded model answers in `replay-outputs.json` go through the real polish pipeline: the prompt
routing, the sanitizer, `PolishNormalizer` (dash and emoji repair, substituted numbers and names),
the postprocessor and the finishing steps. Nothing is sent anywhere.

```
swift build --product Flow        # from the repo root; builds .build/debug/Flow
FLOW_EVAL_SUPPORT_DIR=/some/private/dir/ .build/debug/Flow --polish-eval \
  Tests/PolishEval/polish-eval-cases.json OUT.json \
  -voice.allowCloudPolishing YES -voice.privacyMode NO -voice.cleanupModel qwen3 \
  -voice.evalCloudOnly YES -voice.polishReplay Tests/PolishEval/replay-outputs.json
python3 scripts/score-polish-eval.py Tests/PolishEval/polish-eval-cases.json OUT.json --show
```

- `FLOW_EVAL_SUPPORT_DIR` gives the eval its own single-instance lock folder (700 permissions),
  so it runs beside the installed app. It is honoured only with `--polish-eval`.
- `replay-outputs.json` is generated by `make_replay.py`. Most answers are the ideal output. The
  19 hand-written faults are listed in `replay-faults.json` with `guard` (the code must catch it)
  or `gap` (no guard today).
- A `null` answer is a failed cloud call. The fast path is off in eval mode, so every case reaches the model step.
- `test_replay_eval.py` runs all of the above and pins the failing checks to a known list.
  Run with `python3 -m unittest Tests/PolishEval/test_replay_eval.py`.

## 2. Live cloud (needs a Cerebras key, never run without one)

The same command without `-voice.polishReplay`, plus `-cerebrasAPIKey "$KEY"`. Not run yet: no key on this Mac.
Live results measure the prompts, which replay cannot.

## Scoring

`scripts/score-polish-eval.py` runs the mechanical checks: `cloud`, `keep`, `drop`, `dash`, `emoji`,
`preamble`, `casing`, `ending`, `length`, `nonempty`. Meaning is a separate 0/1/2 judgment file passed
with `--meaning`.

`test_polish_eval_cases.py` validates the case file.

## Known results (replay, 14 Nov 2026)

56 of 58 cases pass with the recorded answers, and the code guards in place. The two that do not pass are expected:

- `list-03`: a null (failed cloud) answer, expected.
- `sel-03`: selected text with a swapped number is refused, expected.

What changed in the polish pass (all 14 Nov 2026):

- Speaker wording. A polish may not swap the speaker's unit word for a symbol ("kilos" to "kg",
  "percent" to "%"), change the day order of a date ("12th of March" to "March 12"), add a sentence
  the speaker did not say, drop two or more content words, or end a sentence on a dangling word.
  The unit and date rules apply at every level. The added, dropped and dangling-word rules are
  checked on the light and medium paths only; `high` is the restructuring brief. A spoken correction ("no wait")
  skips the dropped-word rule. A rejected polish falls back to the cleaned original.
  Guard: `speakerWordingProblem` in `PolishPipeline.swift`.
- Dashes. A dash between two days, months, quarters or clock times reads "to" ("Monday to Thursday").
  A dash between two numbers stays a hyphen ("9-5"). A full stop only comes from two clear sentences.
- Dutch. Detected Dutch passes through unchanged, so `mix-01` expects the raw text.
- Numbers. Spelled-out numbers may still become digits ("twenty five" to "25"), since that is not a
  unit or a date. Units and dates keep the speaker's words.
